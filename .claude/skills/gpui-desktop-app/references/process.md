# Process lessons (planning, parallel workers, hooks)

- Build in dependency order: native foundation (window opens on Wayland, GPU recorded) → text + virtualization inside the real app → workflow → visual system → one batched review → one correction batch → deliver. Risky parts (IME, selection, scroll anchoring) were built inside the shipping components, not as throwaway spikes.
- Fastest path to a coherent product: write the **framework-free core first** (types, protocol, state machine, tests), then the `Model` entity + effect handler, then hand off.
- **Parallel workers:** give each an owned directory (`services` = pipkin-app; `composer` = `text/`; `transcript` = `transcript/`; shell stayed with the lead). Pre-create empty module stubs and `lib.rs` `pub mod` lines so nobody edits shared files. Dependency lines are append-only edits to the shared `Cargo.toml` (one worker appended into `[dev-dependencies]` by accident; check). All workers compile the same crate, so one worker's half-written file breaks everyone's `cargo check`: tell them to wait and retry, not fix files they don't own. Specify the **API contract** (constructors, events, semantics) in the prompt; the composer and transcript came back matching the shell's calls with no integration rework.
- A late cross-cutting request (single-line mode for palette/rename/search) was sent to the owning worker by message; the other worker reported it as a gap rather than editing a file it didn't own. Route such requests explicitly.
- Hand-back reports are model output: verify (we re-ran `cargo test --workspace`, clippy, and a real launch).
- Treat the Zed checkout as read-only reference. Read its source right before implementing the counterpart (the plan's "source reading map").
- Stop hooks / goals can keep firing when remaining work needs the user's approval. Ask a direct question (AskUserQuestion) listing the exact actions (install IME+Orca, change display scale, minimize/restore), respect "None", and say how to end the loop (`/goal clear`). Don't invent workarounds.
- Report incidents plainly (focus theft, a window you moved) in the final summary and the scorecard.
